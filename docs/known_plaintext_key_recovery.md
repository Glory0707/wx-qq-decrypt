# 已知明文搜钥：QQ NT 派生密钥内存恢复

> 适用：QQ NT 9.9.x（实测 9.9.35-52892）。当 hook 抓 passphrase 的方案不可行时（进程拒绝注入、
> 登录窗口错过、或 passphrase 与库对不上号），用本方法直接从**任意可读内存**恢复每库独立的
> 派生 AES-256 密钥 —— 无需 passphrase、无需注入。

## 背景

QQ NT 每个聊天库（nt_msg / group_info / profile_info / ...）使用独立的 SQLCipher passphrase，
由服务器按账号 + key_meta 下发，**登录后客户端会主动从内存清除**。社区通用方案是 hook
`nt_sqlite3_key_v2` 在开库瞬间抓 passphrase（见 `qq_hook*.js`），但有三个失效场景：

1. 部分子进程（如 QQEX.exe / 受保护组件）拒绝 frida-agent 注入
2. 自动登录场景下开库发生在脚本挂钩完成之前（竞态）
3. 多进程架构下 passphrase 只在持有该库连接的进程内存里出现，hook 到的登录期密钥未必是目标库的

关键观察：**passphrase 只是 KDF 输入，真正解密用的是派生后的 AES-256 密钥**。
派生密钥在数据库连接存续期间必然常驻持库进程内存（SQLCipher 每页解密都要用它），
且只需要 `PROCESS_VM_READ` 就能读到 —— 而这个权限 QQ 不设防。

## 原理

SQLCipher 页 1 解密后的明文头是高度可预测的：

```
偏移 0..15 (SQLite 页头前 16 字节):
10 00 02 02 50 40 20 20 00 00 00 XX 00 00 00 XX
│  │  │  │  │  │  │  │
│  │  │  │  │  │  │  └─ 64 (最小/最大 payload 分数 32/32)
│  │  │  │  │  └────── 40 (叶分片 0x20)
│  │  │  │  └────────── 0x50 (保留空间 = reserve 80: IV16+HMAC-SHA512 64)
│  │  │  └────────────── 02 (WAL 模式: file change counter 后读写版本均 2)
│  │  └────────────────── 页大小 4096 的高字节 (10 00 = 4096 大端)
│  └────────────────────── 00
└────────────────────────── 10 00 = 页大小 4096
```

即页大小 4096 + WAL + 特定保留字节的组合构成 8 字节强指纹。
QQ 9.9.35 的所有库均为 `10 00 02 02 50 40 20 20`。

判定式（`qq_scan_db.py`）：

```python
pt = AES.new(K, AES.MODE_CBC, IV).decrypt(CT)
if pt[:2] == b"\x10\x00" and pt[5] == 0x40 and pt[6] == 0x20 and pt[7] == 0x20:  # 命中
```

其中 `CT = 密文页 1 的前 16 字节`（文件头 1024B 私有头之后的盐后首块），
`IV = 密文页 1 尾部 reserve 区的 IV（偏移 -48..-32）`。

误报率分析：AES-256 下随机 32 字节解出固定 8 字节指纹的概率为 2^-64，
滑窗过 1GB 内存（~2^30 窗口）误报期望 ≈ 2^-34，实际为零；且命中后会二次打印
明文头供人工复核。

## 流程

```
1. 定位持库进程
   └─ 扫各 QQ 进程内存找表名明文 ("group_msg_table" / "c2c_msg_table")，
      计数最高者即持库进程（页缓存在 SQLITE_OPEN 页里以明文存在）
2. 对该进程做逐区域 32B 滑窗 + 熵预筛 (set(bytes)>=12) + AES 试解
3. 命中 → 存 hex 到 local/qq_derived_keys/<db>.key
4. qq_decrypt_db.py: 剥 1024B 头, 每页 [密文4048][IV16][pad12][HMAC20] AES-CBC 解密
```

实测性能：1 GB 内存、10 进程池，约 15~50 分钟/库（取决于进程内存膨胀程度与命中位置）。

## 实测结论（2026-09，QQ 9.9.35-52892，Windows 11）

| 结论 | 说明 |
|---|---|
| 每库独立密钥 | nt_msg / group_info / profile_info / collection 四库派生密钥互不相同（本会话实测 4/4 不同；意味着旧版"一钥解全库"路线彻底失效，须逐库恢复） |
| 密钥复现方式 | 对同一库在不同进程内存中重复扫描，命中同一 hex 值（同会话内 passphrase 不轮换）；跨会话（退出重登）后 4 库密钥中已复验 1 库（nt_msg）不变，其余库的跨会话稳定性未单独复验 |
| 密钥跨会话稳定 | 同一账号同一次登录内，捕获的派生密钥在新进程（重登后）中仍出现（值不变） |
| 派生密钥直接可用 | 拿到 enc key 后无需 passphrase，页解密 integrity_check = ok |
| hook 抓到的 ≠ 全部 | 登录期 hook 命中的 2 个 passphrase 均无法通过 sqlcipher 校验 nt_msg——它们属于其他库或别的进程 |
| 页1指纹具有版本稳健性 | 指纹只依赖页大小/WAL/reserve，不依赖偏移量，比特征码更抗版本更新 |
| 1024B 私有头 | protobuf 结构，含 128 hex 字符的 key_meta（服务器换取密钥的凭证）与算法自描述（`HMAC_SHA1`） |

## 发现：每库密钥独立（对比微信）

这是与微信 4.x 完全不同的密钥管理模型，也是 QQ 侧恢复成本更高的根源：

| | 微信 4.x | QQ NT 9.9.35 |
|---|---|---|
| 密钥粒度 | **一个账号一把**，27 个库（contact/message/session/...）全部共用 | **每个数据库独立一把** |
| passphrase 来源 | 本地固定，登录后校验 | 服务器按各库文件头中的 `key_meta` 下发，可轮换 |
| 恢复一次能解多少 | hook 一次 → 全库离线解密 | 只解密抓到钥的那一个库 |

实测证据（2026-09，同一账号同一次登录会话）：

- nt_msg / group_info / profile_info / collection 四库分别搜出的派生密钥**两两不同**（四个 32B 值互不相等）
- 交叉验证失败：拿 nt_msg 的派生密钥解 group_info 页 1，HMAC 校验不通过；反之亦然
- 登录期 hook 命中的 2 个 passphrase 均无法通过 nt_msg 页 1 校验——它们属于其他库的连接

机制解释：每个库文件头的 1024B 私有头各自携带独立的 `key_meta`（128 hex 字符），
客户端以此向服务器（OIDB `0xcde`）换取当次 passphrase——"一库一 meta 一钥"是协议设计使然，
并非实现疏漏。

实际影响：

- 微信：密钥抓取一次即可全量离线解密，重跑 `decrypt` 即含最新消息
- QQ：必须让**目标库的连接**在抓钥时存活；冷门库（recent_contact、files_in_chat 等）
  平时并不保持打开，需先在 UI 中触发对应功能（如打开"文件"标签页）再执行搜钥

## 使用

```bash
# 找持库进程（打印 HOLDER: <pid> <标记数>）
# 然后对目标库扫钥（~15-50 min）
python qq_scan_db.py nt_msg.db <持库pid>

# 解密（读取 local/qq_derived_keys/<db>.key）
python qq_decrypt_db.py nt_msg.db
```

## 局限与注意

- 派生密钥随 passphrase 轮换（服务器重新下发）而变化；换设备登录后需重新捕获
- 需要目标库的连接处于打开状态（QQ 前台正常使用即为真；数据库是按需开关的，冷门库可能要先在 UI 里触发）
- 本方法仅用于恢复**本人账号**在本机的数据；对他人设备使用涉及法律风险
