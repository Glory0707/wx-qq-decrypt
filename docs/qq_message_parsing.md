# QQ NT 消息体解析：40800 列 protobuf → 可读文本

> `qq_parse_msg.py`。解密后的 `c2c_msg_table` / `group_msg_table` 中，
> 消息正文存在 `40800` 列（BLOB），为 **无 schema 的 protobuf** 编码。
> 本脚本零依赖（纯标准库）把它还原成可读文本/结构化 JSON。

## 数据形态

- QQ NT 直接用 proto 字段号做数据库列名（`40800`、`45101`、`45402`...），
  字段号即语义 key——这与常规"字段号→名称映射表"的用法相反，反而省了 schema
- `40800` 内部是嵌套 protobuf：正文/引用/图片/文件等各占一个子字段
- 消息类型在 `45002`（主类型）+ `45003`（子类型），最常见: 1=文本 2=图片 3=文件
  4=语音 5=视频 6=QQ表情 7=引用 8=灰条提示 9=红包 14=Markdown 21=通话 27=戳一戳

## 解码器设计（v2）

### 1. 无 schema 递归解码

`raw_decode()` 按 protobuf wire format 逐字段读 varint tag → 按 wire type 取值；
wire type 2（length-delimited）的 value 再尝试递归解码，失败则按 bytes 处理。
不需要 .proto 文件，不需要 blackboxprotobuf。

### 2. 失败重同步 walker（resync）

嵌套层一多，边界误判不可避免。v1 遇错整体 return 会丢掉后续全部字段；
v2 改为**失败后字节 +1 重同步**：从出错点向前挪 1 字节重试解析，直到耗尽缓冲。
实测把解析失败率压到 161 万条中 2 条（0.0001%），且剩余字段全部恢复。

### 3. utf-8 优先 + GBK 修复链（带二次乱码门槛）

文本字段按顺序尝试：

```
utf-8 成功 → 采用
utf-8 失败 → GBK 试解 → 过 mojibake 门槛 → 采用 / 否则按原 bytes
```

**门槛的必要性**：UTF-8 中文被误按 GBK 解出来会呈现典型乱码
（锛/鍗/浠/婃/閮/娈/鑾/鐜/鍚/鐨/勬/垜/璇/翠/綘 等字），如果无门槛放行，
正常的 GBK 文本没问题，但一旦 UTF-8 解码"意外成功"（如 ASCII+少量汉字混排），
GBK 分支可能产出二次乱码。门槛规则：

- 命中特征字符 ≥ 2 个 → 拒绝 GBK 结果
- 命中 `锛`（全角标点被误解码的最常见产物）→ 直接拒绝

> 注：极少数源数据在 QQ 收到之前就已损坏（blob 内含 U+FFFD，如复制粘贴丢失编码的
> IDE 报错文本），属于源头问题，解码层无法修复。

## uid → 昵称映射

消息行里只有 uid（`0000...` 形态的内部 id）。脚本启动时从解密后的
`profile_info_plain.db` / `group_info_plain.db` 的资料表构建 uid→昵称映射，
导出文本中直接显示昵称；无映射的 uid 原样显示。

## 输出

```bash
python qq_parse_msg.py                  # 全量导出 txt
python qq_parse_msg.py --json out.json  # 另存结构化 JSON
```

- 文本行格式：`[时间] 群号/会话 昵称(uin): 内容`，多元素用 ` | ` 连接
  （如 `[引用] xxx | @某人 | 正文`）
- 单聊+群聊 161 万条约 1.5 分钟跑完（纯 Python，逐条 try/except 隔离）

## 已知局限

- 源头损坏（blob 已含 U+FFFD）无法修复，会原样带 `\ufffd` 输出
- 语音转文字（45923）仅当服务器返回过转写才有值
- 灰条/卡片等复杂元素按摘要输出，不逐字还原 XML/JSON 全文（需要时用 --json 自取）
